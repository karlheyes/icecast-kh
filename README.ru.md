# Icecast-KH22: исправления стабильности

[English](README.md) | Русский

Собственная сборка **2.4.0-kh22-p4** на базе
[Icecast-KH22](https://github.com/karlheyes/icecast-kh/tree/bb4173850be18466adc3c8b12a3b08d4b4ba1a55).
Сохранены история upstream, авторство и лицензия **GPL-2.0**:
[COPYING](COPYING), [AUTHORS](AUTHORS), [исходный README](README).

## Исправления

- Mount-specific admin-запрос к подключающемуся relay возвращает HTTP 400
  `Source is not available`, если у source ещё нет worker. Блокировка source
  освобождается до формирования ответа. После подключения relay административные
  команды и подробная статистика снова доступны.
- XSLT после URL-аутентификации использует независимые часы при отсутствии
  worker и возвращает запрос в очередь обработки. Ошибки шаблонов дают HTTP 404;
  перед отправкой ошибки очищается ссылка `aux_data` на XSLT-запрос.
- `listclients` и `listclients.xsl` после успешной source URL-аутентификации
  обрабатываются как admin-запросы. Исправление основано на
  [upstream PR #431](https://github.com/karlheyes/icecast-kh/pull/431).
- Выдача файлов с ограничением скорости после URL-аутентификации не вызывает
  падение; после неудачной перезагрузки сертификата продолжает работать прежний
  TLS-контекст; длинные параметры Safari redirect сохраняются. Исправления
  основаны на upstream-коммитах `a8cfaae`, `c7aeda5` и `ea3554b` соответственно.
- Включены все изменения после KH22 из `master` форка на `ea3554b`: очистка
  очереди, настроенный Server header и обновления CORS. Публичный CORS использует
  `*` без credentials; для доступа с credentials нужен явно настроенный origin.
  Редиректы также содержат `Vary: Origin`.

Проверка NULL-worker и использование `timing_get_time()` основаны на
[предложении RexViber, upstream issue #478](https://github.com/karlheyes/icecast-kh/issues/478).
Здесь дополнительно обеспечена постановка запроса на worker: одного изменения
часов недостаточно для доставки ответа после URL-аутентификации.

## База и совместимость

База — commit `bb4173850be18466adc3c8b12a3b08d4b4ba1a55`, тег
`icecast-2.4.0-kh22`, используемый рецептом Icecast в AzuraCast 0.24.0.
Изначально форк был клонирован с `master` на `ea3554b`; между базой KH22 и этим
commit десять коммитов, затрагивающих девять файлов. Все они включены с сохранением
истории вместе с исправлениями стабильности форка и описанной ниже защитой CORS.
Коммит `f23606b` сохраняет p3 до объединения.

[Разбор изменений после KH22](docs/upstream-review.md) содержит оценку этих коммитов,
исходное сравнение и проверки последующей интеграции (на английском).

Сохраняются протоколы SOURCE, MP3/AAC, relay, metadata, fallback, XML stats
и список слушателей с IP/User-Agent. Изолированные тесты проверяют эти сценарии.
Отчёт о проверках отдельно описывает тест демостанции p3 и проверки p4.
Работающая установка пользователя и воспроизведение в браузере не проверялись.

## Настройка CORS

По умолчанию публичный поток доступен с любого browser origin без credentialed
CORS. Icecast не отражает произвольный origin запроса и не разрешает ему чтение
с credentials. Проверка паролей сохраняется.

Если доверенному веб-клиенту нужен CORS с credentials, укажи фиксированный origin
через существующую глобальную настройку или настройку mount. Нужны точные схема,
хост и порт клиента, без завершающего слеша:

```xml
<http-headers>
    <header name="Access-Control-Allow-Origin"
            value="https://player.example.org" />
</http-headers>
```

Проверь нужные mounts и admin-ответы, включая заголовки reverse proxy.
Пример разрешает один origin, а не список.
Различие wildcard и credentialed CORS задаёт
[стандарт Fetch](https://fetch.spec.whatwg.org/#http-access-control-allow-credentials).

## Работа с репозиторием

`master` — целевая ветка для проверенных изменений форка. Временные ветки
создаются от неё и возвращаются через pull request в `master` этого репозитория.
Обновления upstream объединяются во временной ветке с сохранением истории;
перед слиянием проверяется общий результат. Для текущего PR используется merge
commit: он сохраняет точку p3 и историю upstream. PR автору оригинала необязателен.

Для скачиваемой версии проверенный коммит отмечается тегом `v2.4.0-kh22-pN`,
а к GitHub Release прикладываются готовый архив и `SHA256SUMS`. Бинарники в Git
не хранятся. До проверки целевого окружения кандидат публикуется как prerelease.
Текущее объединение не публикует выпуск и не устанавливает сборку.

## Сборка и проверки

Требуются Bash, Git и Docker Engine с доступом к Docker socket.
Сеть нужна только для скачивания базового образа и build dependencies.

```bash
bash tests/check.sh
```

Скрипт собирает исходный KH22 и исправленную версию из чистых исходников,
проверяет ожидаемые SIGSEGV исходной версии и успешные ответы исправленной.
Runtime-контейнеры работают от `nobody`, с `--network none`, без опубликованных
портов и host volumes, с read-only root, временным `/tmp`, ограничениями
256 MiB RAM, одного CPU и 96 PID, без core dumps и Linux capabilities.
HTTP upstream и URL-auth сервис существуют только на loopback контейнера.
Аудио — синтетическая синусоида, MP3/AAC генерируются установленным ffmpeg.

Проверяются:

- 100 admin-запросов в окне подключения relay, контрольные запросы без relay
  и общий `/admin/stats`;
- подключение и повторное подключение relay, декодирование аудио, metadata,
  общий счётчик и подробный список слушателей с IP/User-Agent;
- обычный и URL-auth XSLT для корректного, отсутствующего, повреждённого
  и аварийно завершающего преобразование шаблона; по 60 повторных запросов
  с параллельностью 6, успешный запрос после ошибок и admin XSLT;
- SOURCE MP3/AAC, metadata, статистика слушателей, fallback и SIGTERM.
- `listclients` с успешной и отклонённой source URL-аутентификацией;
- файлы с ограничением скорости и URL-аутентификацией, TLS после неудачной
  перезагрузки сертификата и Safari redirect с короткими и длинными параметрами;
- CORS для admin, потока, redirect и OPTIONS с настройками по умолчанию и
  фиксированным origin, без credentials, без origin и с посторонним origin;
- 120 секунд с восемью быстрыми и четырьмя медленными слушателями: размер очереди
  и RSS, отключение и повторное подключение медленных клиентов, непрерывность
  быстрого воспроизведения и перезапуск source.

В `artifacts/` сохраняются логи обеих сборок и проверок, install archive,
SHA-256 архива и бинарника, ID образа и diff исправлений. Каталог исключён из Git.
Результаты конкретной проверки фиксируются в [docs/validation.md](docs/validation.md)
на английском языке.

Отдельная сборка без regression-тестов:

```bash
docker build -f tests/Dockerfile -t icecast-kh:kh22-p4 .
```

Install archive содержит дерево `usr/local/`, включая бинарник, стандартные
web/admin-шаблоны, пример конфига и лицензию. Это артефакт для проверки и
последующей интеграции; распаковка поверх рабочего окружения не входит в процедуру.
Тестовый образ также содержит compiler и ffmpeg и предназначен для стенда.

Нативная сборка с зависимостями, перечисленными в исходном README:

```bash
./configure
make clean
make -j2
make check
./src/icecast -v
```

Файл `version` задаёт суффикс `p4`. После изменения кода для новой публикации
нужно изменить release suffix. Для контейнерной сборки он переопределяется
через `--build-arg RELEASE=...`. Чистая сборка обязательна: старый исследовательский
кандидат пропустил перекомпиляцию `admin.c` из-за одинаковых временных меток.

Digest Python base image закреплён в `tests/Dockerfile`; версии Debian-пакетов
не закреплены snapshot-репозиторием. Команды воспроизводимы, побитовая
воспроизводимость артефактов не заявляется. Проверки не заменяют полный аудит
безопасности и длительное тестирование под рабочей нагрузкой.
